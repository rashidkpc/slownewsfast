# slownewsfast

Turn things into Atom feeds. Two kinds of feed today:

- **Newsletter feeds** — get an email address, subscribe to newsletters; each email becomes an entry. (A Cloudflare-native replacement for kill-the-newsletter.)
- **Digest feeds** — point at any RSS/Atom feed; it polls often to catch everything, then publishes **one entry per schedule** bundling what it collected.

## Architecture

| Layer | Technology |
|---|---|
| Email ingest | Cloudflare Email Routing → Worker handler |
| Digest ingest | Cron Worker → source feed poller, images to R2 |
| Database | D1 (serverless SQLite) |
| Attachments | R2 (object storage) |
| Web UI | React + Tailwind CSS v4, served via Workers Static Assets |
| API + feed generation | Cloudflare Worker (Hono) |
| Auth | HMAC-signed session cookie, single password |
| Cleanup | Cron trigger (every 15 minutes) |

### Producers

A feed is just *something that has entries*. **How** those entries get made is a
*producer*: a row in `feed_producers` with a `kind` and a JSON `config`. The
output side (`feed_entries` + the Atom/HTML renderers) is deliberately generic —
any entry may carry an `image`/`summary`, and one renderer handles them all — so
adding a producer kind is a new handler + a config form, not a schema change.

Current kinds:

| Kind | Entry source |
|---|---|
| `email` | One inbound email (via Email Routing) per entry. |
| `feed_digest` | Polls a source feed into a transient `source_items` inbox, then folds it into one entry per scheduled tick. |

The digest producer keeps a small piece of state: `source_items` is the inbox
(deleted once composed) and `entry_source_items` records which guids a published
entry consumed, so items still sitting in the upstream feed are never re-ingested.
Lead images are fetched into R2 and rewritten to local `/files/...` URLs.

## Prerequisites

- A Cloudflare account with a domain on Cloudflare DNS
- Node.js 18+
- Wrangler CLI (`npm install -g wrangler` or use `npx`)

## Deployment

The instructions below probably work. Or just launch whatever agent CLI thing you have, and make it do the deploy. Nailed it. 

### 1. Clone and install

```bash
git clone <repo-url> slownewsfast
cd slownewsfast
npm install
```

### 2. Enable Email Routing for your subdomain

I run this on a subdomain of my domain. In theory Cloudflare says you have to handle the apex domain via cloudflare too, but this doesn't seem to be the case. The Dashboard may show the apex domain as "misconfigured" or with DNS warnings. This is expected and harmless. Only the subdomain needs to be functional. The subdomain's MX, SPF, and DKIM records are managed independently from the root domain.

In the Cloudflare Dashboard:

1. Go to **Compute → Email Service → Email Routing**
2. Open the **Settings** tab
3. Under **Subdomains**, enter your subdomain (e.g. `slownews`) and submit

Cloudflare automatically adds MX, SPF, and DKIM records to the subdomain. The apex domain is not affected — your existing email provider continues to work. If that's a thing you have.

### 3. Create D1 database

```bash
wrangler d1 create slownewsfast-db
```

Copy the `database_id` from the output and paste it into `wrangler.jsonc` (copy `wrangler.jsonc.example` to `wrangler.jsonc` first and fill in your values).

### 4. Create R2 bucket

```bash
wrangler r2 bucket create slownewsfast-attachments
```

### 5. Set the login password

```bash
wrangler secret put PASSWORD
```

You'll be prompted to enter a password. This is the only password needed to access the web UI. We're not doing multi-user over here. 

### 6. Apply database migrations

```bash
wrangler d1 migrations apply slownewsfast-db --remote
```

### 7. Deploy the Worker

```bash
wrangler deploy
```

### 8. Wire the catch-all routing rule

In the Cloudflare Dashboard:

1. **Compute → Email Service → Email Routing → Routing Rules**
2. Select your subdomain from the domain selector
3. Enable the **Catch-all rule** toggle
4. Set **Action** to **Send to a Worker**
5. Select `slownewsfast` from the dropdown
6. **Save**

### 9. Point DNS to the Worker

You can probably just use the autogenerated pages.dev url too, but I didn't test it.

1. **Compute → Workers & Pages → Domains**
2. Click **Add domain** 
3. Point at your subdomain or whatever. 

## Usage

1. Visit `https://slownews.yourdomain.com` and sign in with your password
2. Create a feed:
   - **Newsletter** — you get a unique email address and an Atom feed URL. Use the email when subscribing to newsletters.
   - **Digest** — give it a source RSS/Atom URL, a schedule (cron + timezone), and whether to include full article content. It polls often and publishes one entry per tick.
3. Add the feed URL to any feed reader (NetNewsWire, Feedly, slowreader, etc.)

### Digest feeds in a bit more detail

- **Polling vs. publishing** are decoupled: it polls on the interval you set (default 30 min) so nothing rolls off the source feed, and publishes on your cron schedule (default daily midnight in the chosen timezone).
- **Late items carry over** into the next digest; items already published are never repeated.
- **First digest** can either backfill everything currently in the source feed, or start from now.
- **Images**: the lead photo of each item is stored in R2 (toggle per feed) so it doesn't vanish from the source; inline images are left as source URLs for now.
- **Feed icon** comes from the upstream source when it provides one (RSS `<image>`, Atom `<logo>`/`<icon>`, else its favicon).

### Feed URLs are public

Feed URLs (`/feeds/*.xml`, entry pages, and file attachments) are publicly accessible so they work with any feed reader. Only the web UI and API require authentication. We're doing security through obscurity up in here. I mean honestly, authenticated Atom feeds? GTFO.
